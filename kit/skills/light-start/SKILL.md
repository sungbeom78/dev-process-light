# light-start — 시작하기 전에 합의

## 언제
- "○○ 기능 만들어 줘", "○○ 바꿔 줘" 같은 요청을 받았을 때 -- **코드를 쓰기 전에**
- 오타·문구·색 하나 바꾸기처럼 아주 작은 일은 생략하고 바로 해도 된다 (그래도 끝나면 light-check)

## 순서
1. `dev-notes/FEATURES.md` 를 본다. 이번 요청이
   - 새 기능인지, 기존 기능을 바꾸는지
   - 어떤 파일을 건드릴지, 그 파일을 **다른 기능도 쓰는지** ("함께 쓰는 파일" 포함)
   - 저장하는 데이터가 생기거나 바뀌는지 (`NOW.md` 의 "저장하는 데이터", `FEATURES.md` 의 "데이터 (표)" 절)
   를 확인한다.
2. 요청이 크면 나눈다. 기준: **한 단계 = 30분 안에 만들고 확인할 수 있는 크기**, 단계마다 저장한다.
   예) "가계부" → ① 입력과 목록 ② 월별 합계 ③ 그래프
3. 작업 카드를 만들어 `dev-notes/NOW.md` 의 "지금 작업" 에 적고, 사용자에게 보여준다:
   ```
   ### 작업: 할 일 목록 (1/3 입력과 목록)
   - 목표: 할 일을 적고 체크할 수 있다
   - 완료 기준:
     - [ ] 할 일을 입력하고 Enter 를 누르면 목록에 추가된다
     - [ ] 체크하면 줄이 그어진다
     - [ ] 새로고침해도 목록이 남아 있다
   - 건드릴 기능: 할 일 (새 기능) -- 새 파일 todo.js, index.html 에 메뉴 1줄 추가
   - 영향 받을 수 있는 기능: 메모 (index.html 을 같이 씀) -- 끝나고 메모도 점검
   - 설명서: 장 추가 (manual/todo.html)
   - 데이터: 브라우저에만 (저장 이름 todos -- NAMES.md 에 적음)
   - 진행: 계획
   ```
   완료 기준은 **사람이 화면에서 직접 확인할 수 있는 문장**으로 쓴다 ("코드가 깔끔하다" 같은 것은 안 된다).
   `설명서:` 는 새로 만듦(처음) / 장 추가(새 기능) / 고침(사용 방법이 바뀜) / 해당 없음(이유) 중 하나 (`light-manual`).
   `데이터:` 는 없음 / 브라우저에만 / 새 표 / 표 바꿈 / 읽기만 중 하나 (아래 "저장할 데이터가 생기면").
4. "이대로 진행할까요?" 라고 묻고, 사용자가 고치면 카드를 고친다. **확인받기 전에는 만들지 않는다.**
5. 새 이름이 필요하면 `dev-notes/NAMES.md` 를 보고, 없으면 카드와 함께 제안한다.
6. 확인받으면 진행을 "만드는 중" 으로 바꾸고 기록한다:
   - 사용자가 정한 것(무엇을 넣고 뺄지 등)은 `DECISIONS.md` 에 `[사용자]` 로 **사용자의 말 그대로**.
   - AI 가 정한 기술 선택(어떤 방식으로 저장할지, 어떤 라이브러리를 쓸지 등)은 `[AI]` 로 이유와 다른 안을 함께,
     그리고 사용자에게 한두 줄 쉬운 말로 알려 준다 ("이번엔 브라우저에 저장하는 방식으로 할게요 -- 서버가 필요 없어서요").
   - 기록 세 층(`light-save` 의 "기록하는 법"): 흐름 `· 기획 · <기능> · <작업 제목> 카드 · 확인받음 · 사용자`,
     그 기능·날짜 파일에 목록 한 줄과 자세히(목표·완료 기준·사용자 답). 그리고 `light-save` 로 `중간 저장:` 한다.

## 만드는 동안
- 카드에 적은 파일만 고친다. 다른 기능의 파일을 고쳐야 할 것 같으면 **멈추고 먼저 말한다.**
- 사용자가 중간에 요청을 바꾸면 카드를 먼저 고치고 다시 확인받는다.
- 한 덩어리를 만들 때마다(30분 안쪽) 기록(흐름 `· 만들기 ·` 한 줄 + 목록 + 자세히: 고친 파일·클래스·함수·변수)을 남기고 `중간 저장:` 한다.
- 다 만들면 `light-check` 로 간다. "다 됐습니다" 라고 먼저 말하지 않는다.

## 저장할 데이터가 생기면 -- 짝 스킬 `data-light` 로 넘겨주기
`data-light`(data-expert-framework-light)는 이 규칙과 짝인 데이터 설계 스킬이다. 같이 설치되어 있다 (`.claude/skills/data-light`).
카드의 `데이터:` 는 아래 중 하나다.

| 데이터 | 언제 | 하는 일 |
|---|---|---|
| 없음 | 저장하는 것이 없다 (화면·글·모양만) | -- |
| 브라우저에만 | 이 기기 브라우저에 간단한 목록 하나 (메모·할 일 정도) | 저장 이름을 `NAMES.md` 에 적는다. 이름·모양을 바꾸면 쓰던 데이터가 안 보일 수 있다고 카드에 적고 먼저 말한다 |
| 새 표 | 아래 "넘겨줄 때" 에 하나라도 해당 | **이 일의 첫 단계가 데이터 설계** -- `data-light` 로 정본을 만들고 확인받은 뒤에 화면을 만든다 |
| 표 바꿈 | 이미 있는 표·칸을 더하거나 바꾸거나 뺀다 | 정본부터 고친다. `FEATURES.md` 데이터 절에서 그 표를 쓰는 기능을 찾아 "영향 받을 수 있는 기능"에 적는다. 데이터가 든 표·칸을 빼거나 이름을 바꾸면 그 데이터가 사라질 수 있다고 먼저 말한다 |
| 읽기만 | 있는 표를 보여 주기만 | 정본의 표·칸 이름을 그대로 쓴다 |

넘겨줄 때 -- 하나라도 해당하면 `data-light`:
- 표가 둘 이상이고 서로 이어진다 (손님 → 주문, 회원 → 회비)
- 여러 기기·여러 사람이 같은 데이터를 본다 (로그인, 서버, Supabase)
- 엑셀·CSV 를 넣는다
- 개인정보(이름·연락처·주소 등)를 저장한다
- 브라우저에만 두던 데이터가 위에 해당하게 자랐다 (옮길 때 쓰던 데이터를 어떻게 할지 먼저 묻는다)

넘겨주는 순서:
1. 큰 일을 나눌 때 데이터 설계를 **1단계**로 둔다. 예) "동아리 회비" → ① 데이터 설계 ② 회원 명단 ③ 회비 입력 ④ 미납 보기.
   데이터 설계 카드의 완료 기준은 "그림과 표를 보고 맞다고 했다", "`verify` 통과" 처럼 확인할 수 있는 문장으로.
2. `NOW.md` "이 프로젝트는" 의 답(누가 쓰나·로그인·올리는 곳·개인정보)을 그대로 쓴다 -- **이미 답한 것은 다시 묻지 않는다.**
   `(아직 모름)` 인 것만 한 번에 하나씩 쉽게 묻고, 답을 그 줄과 `DECISIONS.md`(`[사용자]`, 답 그대로)에 적는다:
   - 누가 쓰나요? -- 나 혼자 / 몇 명이 같이 (누구) / 아무나 가입해서
   - 로그인해서 쓰나요? -- 아니요 / 네 (각자 아이디로)
   - 어디에서 쓰나요? -- 내 컴퓨터에서만 / 인터넷에 올려서 (GitHub Pages 같은 무료 호스팅·Supabase 등) / 잘 모름 (AI 가 추천)
3. **실제로 어디에 저장할지** -- 답에 따라 AI 가 정하고 `NOW.md` "저장하는 데이터" 줄과 `DECISIONS.md`(`[AI]`, 이유·다른 안)에 적는다.
   설계(정본)는 어느 경우든 `data-light` 로 하고, 화면이 실제로 읽고 쓰는 곳만 다르다:

   | 답 | 화면이 읽고 쓰는 곳 | "저장하는 데이터" 줄 |
   |---|---|---|
   | 혼자 · 인터넷 정적 호스팅(GitHub Pages 등) | 그 기기의 브라우저 저장소 -- 정본의 표·칸 이름 그대로 (`data/app.db` 는 만들지 않는다 -- verify 는 메모리에서 시험한다) | `data-light 설계 · 실제 저장은 브라우저` |
   | 혼자 · 내 컴퓨터에서만 | SQLite `data/app.db` + 내 컴퓨터에서 도는 작은 서버(파이썬 등) | `data-light 설계 · SQLite (data/app.db)` |
   | 여럿이 · 로그인 | Supabase (PostgreSQL) -- 정본은 `"db": "postgresql"` | `data-light 설계 · Supabase` |
   | 여럿이 · 로그인 없음 | 로그인을 넣자고 권한다 -- 로그인 없이 여럿이 쓰는 저장소는 주소만 알면 누구나 읽고 바꿀 수 있다고 그대로 말하고, 사용자가 고르게 한다 | (사용자 답대로) |
   | 이미 쓰는 DB 가 있음 | 그 DB -- 아래 "이미 DB 가 있으면" | `data-light 설계 · <그 DB>` |

   브라우저 저장이면 DB 가 규칙(필수·선택값·가리킴)을 지켜 주지 않는다 -- 화면 코드가 지켜야 하므로 그 기능 카드의 완료 기준에 넣는다
   (예: "이름을 비우고 저장하면 막힌다"). 또 데이터는 **그 기기·그 브라우저에만** 있고 사이트 데이터를 지우면 사라진다 --
   백업(파일로 내보내기·불러오기)을 만들지 사용자에게 묻고 답을 `DECISIONS.md` 에 남긴다.
4. `data-light` 의 흐름(이해 → 설계 → 확인)을 따른다. **이미 정한 것은 옮겨 적고 다시 묻지 않는다:**
   카드·`NOW.md` 다음에 할 일에 있는 "데이터로 알 수 있어야 하는 것"(예: 미납 보기 → "이번 달 회비를 안 낸 활동 회원을 볼 수 있다")은
   data-light 의 성공 기준(`goals`)으로, 사용자가 "이번엔 안 한다"고 한 것(카드·`DECISIONS.md`)은 만들지 않을 것(`not_doing`)으로.
   없는 것만 data-light 가 묻고, 답은 `DECISIONS.md`(`[사용자]`)에도 적는다.
   **샘플 행(`sample`)과 성공 기준의 기대 결과(`expect`)는 만든 값으로** 쓴다 -- 가져온 엑셀·CSV 의 실제 이름·연락처를 옮겨 적지 않는다 (정본은 저장되고 올라간다).
   사용자에게는 그림(ERD)·성공 기준 결과·표로 "이렇게 맞나요?" 하고 확인받는다.
5. 확인받으면 고친다: `FEATURES.md` 데이터 절(표 → 쓰는 기능), `NOW.md` "저장하는 데이터"·"개인정보",
   `.gitignore` -- **데이터 줄**, 없는 것만 더한다:
   `data/app.db` `data/backup/` `data/*.csv` `data/*.xlsx` `data/out/spec.xlsx` `data/import_plan*.json` `import_plan*.json` `.env`
   (실제 데이터·원본 파일·가져오기 계획(실제 값이 들어 있다)·비밀 설정은 올리지 않는다. `spec.xlsx` 는 만들 때마다 달라지는 파일이라 다시 만들면 된다).
   **데이터 검사 장치** -- `NOW.md` `## 설정` 에 `데이터 검사 장치:` 줄이 없거나 `(아직 정하지 않음)` 이면 처음 정본을 저장하기 전에 한 번 묻는다:
   "저장할 때마다 데이터 설계를 자동으로 검사하는 장치를 설치할까요? (추천) 설계가 검사를 통과하지 못하면 저장이 멈추고,
   GitHub 에 올리면 거기서도 같은 검사를 해요." 예 → `datalight.py hook install` (`.git/hooks/pre-commit`, `.data-light/datalight.py`,
   `.github/workflows/data-light.yml`, `.gitignore`) -- 결과에 "이미 있어 건드리지 않았습니다" 가 나오면 그대로 사용자에게 알린다(훅이 안 깔린 것).
   아니오 → `안 함`. 답을 `## 설정` 과 `DECISIONS.md`(`[사용자]`, 답 그대로)에 적는다.
   기록하고(아래) `light-save` 로 `데이터:` 저장한다 (정본 `data/model.light.json`, `data/out/`, 장치를 설치했으면 `.data-light/`·`.github/workflows/data-light.yml`).
6. 실제 DB 만들기(`data/app.db`, Supabase 에 적용)와 파일의 데이터 넣기는 **따로 묻고** 답을 받은 뒤에 한다.
   - 이미 있는 DB 를 바꾸기 전에는 `data/backup/<날짜>-app.db` 로 복사해 둔다.
   - 파일 넣기: 파일을 `data/` 안에 두고 `datalight.py import plan data/<파일> --table <표> --out data/import_plan.json` →
     계획의 `"file"` 이 내 컴퓨터의 전체 경로로 적히므로 `"data/<파일>"` 로 고친다 (저장되는 가져오기 기록에 폴더 이름이 남지 않게) →
     계획을 표로 보여 주고 확인 → `import apply ... --approval "<사용자 답 그대로>"`.
   - **Supabase**: **모든 표**에 행 접근 규칙(RLS)을 켜고 누가 무엇을 읽고 쓰는지 규칙(policy)을 둔다 -- `pi_` 표만이 아니다
     (규칙이 없는 표는 사이트에 들어 있는 공개용 키로 누구나 읽고 바꿀 수 있다). 규칙은 "누가 쓰나" 답에 맞춘다:
     정해진 사람끼리(임원 3명 등)면 가입을 막고(초대만) "로그인한 사람만", 아무나 가입하는 사이트면 **자기 행만**(`auth.uid()` 가 주인인 행)
     -- 이때 `pi_` 표는 본인과 관리자만 읽게 한다. 적용한 뒤 Supabase 의 보안 점검(Security Advisor, 도구가 있으면 advisors)에 경고가 없는지 본다.
     사이트 코드에는 **공개용 키(anon·publishable)만**, 관리자 키(service_role·`sb_secret_…`)는 절대 넣지 않는다.
7. 다음 단계(화면)로 돌아온다. 코드는 정본의 표·칸 이름을 그대로 쓴다.

이미 DB 가 있으면 (정본 없이 SQLite 파일·Supabase 를 쓰던 프로젝트): 새로 설계하지 않고 **있는 표·칸을 읽어 정본을 만든다**.
data-light 에는 자동으로 읽어 오는 명령이 없으므로 AI 가 표·칸·자료형·필수·가리킴을 옮겨 적고(`sqlite3 data/app.db .schema`,
Supabase 는 표 목록), `build` 한 SQL 과 실제 DB 를 비교해 다른 점을 사용자에게 보여 주고 확인받는다. SQLite 면 `verify --db <파일>` 로
데이터가 든 표·칸이 정본에서 빠지지 않았는지 본다. DB 자체는 바꾸지 않는다. 이름이 data-light 규칙(영어 소문자·밑줄, `order`·`user` 같은
예약어 금지)에 맞지 않아 `check` 가 막으면 사용자에게 알리고 고르게 한다: DB 의 이름을 바꾸기(확인 후, 그 이름을 쓰는 코드도 함께) /
그 표는 정본 밖에 두기(`FEATURES.md` 에 적어 둔다).
