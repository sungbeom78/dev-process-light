# dev-process-light

**AI와 함께 나만의 홈페이지를 만들 때, 만들수록 망가지지 않게 해 주는 가벼운 작업 규칙.**
Claude Code · Codex 에서 쓰는 스킬 7개와 기록 파일 5장, 저절로 쌓이는 사용설명서와 기록 보기 페이지, 그리고 저장할 데이터가 생기면
이어 받는 **짝 데이터 설계 스킬 `data-light`**([data-expert-framework-light](https://github.com/sungbeom78/data-expert-framework-light)).
설치할 프로그램은 없습니다 (마크다운 + git, 데이터 검사·페이지·설명서 검토에만 파이썬).

[English](README.en.md)

## 이런 분께
개발자는 아니지만 AI(Claude Code, Codex)로 메모·할 일·가계부·사진첩처럼 **기능이 여러 개인 개인 사이트**를 만드는 분.
그리고 이런 일을 겪어 본 분:

- 새 기능을 넣었더니 **예전 기능이 망가졌다**
- 다음 날 이어서 하려는데 **AI가 어디까지 했는지 모른다**
- AI는 "완료했습니다"라는데 **열어 보면 안 된다**
- 망가졌는데 **되돌리는 법을 모른다**
- AI가 같은 오류를 **같은 방식으로 계속 고치려 한다**

## 어떻게 막나요

| 스킬 | 언제 | 하는 일 |
|---|---|---|
| `light-resume` 이어하기 | 시작할 때마다 | 기록을 읽고 "어디까지 했고 다음은 무엇인지" 5줄로 알려 줌. 처음이면 준비 |
| `light-start` 시작 전 합의 | 기능을 만들기 전 | 목표·완료 기준·건드릴 기능을 카드로 정리해 **확인받고** 시작. 큰 일은 작게 나눔 |
| `light-check` 확인하고 끝내기 | "다 됐다" 말하기 전 | AI가 **직접 실행해서** 확인한 것 / 사람이 봐야 할 것 / 확인 못 한 것을 나눠 보고. 다른 기능도 점검 |
| `light-save` 저장 | 단계가 끝날 때마다 (합의·만들기·확인·되돌리기) | 작업 기록 한 줄 + git 에 저장(되돌아올 지점, 미완성은 `중간 저장:`) + 기록 갱신. 정해 두면 인터넷 저장소에도 올림 |
| `light-undo` 되돌리기 | 망가졌을 때 | 저장 목록을 보여주고 고른 지점으로 **기록을 지우지 않고** 되돌림 |
| `light-manual` 사용설명서 | 처음 만들 때 · 새 기능 · 사용법이 바뀔 때 | `manual/` 에 HTML 슬라이드 설명서(그림·단계별 페이지·강의 대본)를 만들거나 고쳐 같이 저장하고, **채팅에 보여 줌**. 요청하면 pptx |
| `light-portal` 기록 보기 | 저장할 때마다 · "기록 보여 줘" | 지금 상황·기능·데이터 설계·결정(사용자/AI)·작업 기록·저장 목록을 한 화면에서 보는 HTML 파일 하나 (서버·로그인 없음, 내 컴퓨터에서만) |
| `data-light` 데이터 설계 (짝) | 저장할 데이터가 생길 때 (표가 이어짐·여럿이 로그인·엑셀·개인정보) | 쉬운 질문 몇 개로 표를 설계해 **그림(ERD)과 표로 확인받고**, 검사·규칙 시험·정의서·SQL(SQLite·Supabase)을 만듦. 개인정보는 따로, DB 만들기·엑셀 넣기는 확인 후 |

그리고 `AGENTS.md` 의 규칙 13줄 -- 그중 핵심은 둘입니다:
**다른 기능을 건드리면 먼저 말한다**, **문제가 나면 원인부터 보고(고치기·기다렸다 다시·부탁하기·다른 방법) 끝까지 처리한다 -- 안 되면 되돌리기·빼기·나중에 할 일 중 고르게 한다.**

기록 파일은 `dev-notes/` 에 5장 -- 사람이 읽어도 쉬운 마크다운입니다.

| 파일 | 내용 |
|---|---|
| `NOW.md` 지금 상황 | 이 프로젝트가 무엇인지(+ 스킬들이 같이 쓰는 답 다섯 줄: 누가 쓰나·로그인·올리는 곳·저장하는 데이터·개인정보), 지금 작업 카드, 다음에 할 일, 마지막 저장, 설정(올리기·기록 보기 페이지) |
| `FEATURES.md` 기능 지도 | 기능마다 상태·쓰는 파일·확인 방법 한 줄 -- **다른 기능을 망가뜨리지 않는 핵심**. 데이터 절: 표마다 쓰는 기능 |
| `DECISIONS.md` 결정 기록 | "왜 이렇게 했지?" 한 줄씩 -- `[사용자]` 는 답 그대로, `[AI]` 는 이유와 다른 안 |
| `LOG.md` 작업 기록(흐름) | 단계(기획·만들기·확인·운영·평가)가 끝날 때마다 한 줄: 언제 · 단계 · 기능 · 무엇을 · 결과 · 누가 |
| `log/<기능>/<날짜>.md` | 그날 그 기능에서 한 일의 **목록**(한 줄씩)과 **자세히**(고친 파일·클래스·함수·변수, 확인 결과·오류·해결, 평가). 데이터 설계·변경은 `log/데이터/` |
| `NAMES.md` 이름표 | 화면의 말 ↔ 코드 이름 (같은 것을 여러 이름으로 부르지 않게). 데이터의 표·칸 이름표는 정본(`data/model.light.json`)에 |

기록은 많아지므로 세 층으로 나눕니다: 흐름(`LOG.md`) → 목록 → 자세히. AI 는 지난 일을 볼 때 이 순서로 **필요한 것만** 읽습니다.

## 사용설명서가 저절로 쌓입니다

설명서는 **웹페이지(HTML)** 입니다. 페이지 하나가 16:9 슬라이드 한 장이라 그대로 발표(`P`)·PDF 인쇄·pptx 로 쓸 수 있고,
페이지마다 **그림**(순서도·화면·카드)과 **강의 대본**이 있어 유튜브 영상으로 녹화하기 좋습니다. 사용 방법은 **한 단계 = 한 페이지**.

| 이번 작업 | 설명서 (`manual/`) |
|---|---|
| 처음 만듦 | **새로 만듦** -- 목차(`README.md`: 시작하기·기능 목록·바뀐 점) + 기능별 장 |
| 새 기능 추가 | **장 추가** -- `manual/<기능>.html` + 목차 |
| 화면 흐름·사용 방법 변경 | **고침** -- 바뀐 단계 + "바뀐 점" 한 줄 |
| 버그 수정(사용법 같음)·정리·색만 바꿈 | 해당 없음 (작업 카드에 이유) |

AI는 설명서의 **따라 하기를 실제로 해 보고** 저장한 뒤, 바뀐 부분을 채팅에 그대로 보여 줍니다.
예시: [`examples/my-homepage/manual/`](examples/my-homepage/manual/index.html)

## 저장할 데이터가 생기면 -- 짝 스킬 `data-light`

회원·주문·예약처럼 **표가 둘 이상 이어지거나, 여럿이 로그인해서 쓰거나, 엑셀·CSV 를 넣거나, 개인정보를 저장하면**
화면을 만들기 전에 데이터부터 설계합니다. 그 일은 짝 스킬 `data-light` 가 맡고, 끝나면 다시 light 흐름으로 돌아옵니다.
설치기가 두 스킬을 함께 깝니다.

| | 개발 흐름 | 데이터 설계 |
|---|---|---|
| 가벼운 판 (공개) | **dev-process-light** (이 저장소) | **data-expert-framework-light** -- 스킬 `data-light` |
| 전문판 | dev-process-framework | data-expert-framework |
| 짝을 묶는 법 | 이 저장소가 `data-light` 를 **정해 둔 커밋 그대로** `kit/skills/data-light` 에 담아 함께 설치 ([`data-light.lock.json`](data-light.lock.json)) | 전문판은 서브모듈로 고정 |

지금 짝 버전: **data-light 0.6.4** (data-expert-framework-light `4c62e1f`).

어떻게 이어지나요:
- **질문은 한 번만** -- 누가 쓰나·로그인·올리는 곳·개인정보는 `NOW.md` 의 다섯 줄에 한 번 적고, 어느 스킬도 다시 묻지 않습니다.
  data-light 가 새로 물은 답도 그 줄과 `DECISIONS.md` 에 남깁니다.
- **데이터부터** -- 작업 카드에 `데이터:` 줄(없음 · 브라우저에만 · 새 표 · 표 바꿈 · 읽기만). 새 표면 데이터 설계가 1단계입니다.
- **이미 정한 것은 옮겨 적기** -- 카드의 완료 기준 중 데이터로 확인할 것은 data-light 의 성공 기준(`goals`)으로,
  "이번엔 안 한다"고 한 것은 `not_doing` 으로. 데이터 검사 장치(커밋할 때 `verify`)를 설치할지는 처음 한 번만 묻습니다.
- **정본 하나** -- `data/model.light.json` 만 고치고, 그림(`data/out/erd.md`)·정의서·SQL 은 거기서 만듭니다. 코드는 정본의 이름 그대로.
- **누가 볼 수 있나도 정본에** -- Supabase 면 "누가 쓰나" 답대로 `signup`(새 가입을 끄나)과 표마다 `access`(로그인한 사람 모두 · 만든 사람만 · 누구나 읽기만)를
  정본에 적고, SQL 에 실제 행 접근 규칙이 만들어집니다. 정해진 사람끼리면 Supabase 의 새 가입 끄기를 확인한 뒤에 적용합니다.
- **표를 바꾸면 그 표를 쓰는 기능을 모두 점검** -- `FEATURES.md` 의 "데이터 (표)" 절이 표 ↔ 기능을 잇습니다.
- **확인과 저장** -- `light-check` 가 `datalight.py verify`(설계 검사·성공 기준·규칙 시험·생성물·데이터 보호를 한 번에)를 실제로 돌리고, `light-save` 가 `데이터:` 로 저장합니다.
  실제 데이터(`data/app.db`)·원본 엑셀·`.env` 는 저장하지 않습니다.
- **돌이킬 수 없는 일은 확인 후** -- DB 만들기·바꾸기·지우기, 파일의 데이터 넣기. 설계를 되돌려도 이미 만든 DB 는 그대로라고 먼저 알립니다.
- **다시 설치하면 맞춰 둔다** -- 검사 장치는 `datalight.py hook status` 로 보고 버전이 다를 때만 다시 설치하고, 생성물은 늘 다시 만들어 `verify` 합니다.

따라 하기 예시: [`examples/club-dues/`](examples/club-dues/WALKTHROUGH.md) -- 동아리 회비 사이트의 1단계(데이터 설계)를 실제로 수행한 기록.
data-light 만 따로 쓰고 싶으면 그 저장소의 플러그인으로 설치할 수도 있습니다.

## 설치 (1분)

**가장 쉬운 방법** -- 만들고 있는 프로젝트 폴더에서 Claude Code(또는 Codex)를 열고:
```
https://github.com/sungbeom78/dev-process-light 의 INSTALL.md 를 읽고 이 프로젝트에 설치해 줘
```

**직접 설치** -- git 이 있다면:
```bash
git clone --depth 1 https://github.com/sungbeom78/dev-process-light.git ~/dev-process-light
bash ~/dev-process-light/install.sh <내 프로젝트 폴더>
```
Windows PowerShell 이면 마지막 줄을 이렇게:
```powershell
powershell -ExecutionPolicy Bypass -File $HOME\dev-process-light\install.ps1 <내 프로젝트 폴더>
```
git 이 없으면 이 페이지의 **Code → Download ZIP** 으로 받아 풀고 같은 명령을 실행하세요.

설치기는 **이미 있는 기록(`dev-notes/`)·데이터(`data/`)와 내가 쓴 `AGENTS.md` 내용을 덮어쓰지 않습니다.** 다시 실행하면 스킬(짝 스킬 data-light 포함)만 새 버전으로 바뀝니다.
그래서 `light-*`·`data-light` 스킬과 규칙 블록은 프로젝트에서 고치지 않습니다. **이 프로젝트만의 규칙은 `AGENTS.md` 의 규칙 블록 밖에** 적으세요.

## 사용
설치 후 AI 에게 처음 한 번:
```
light-resume 으로 시작해 줘
```
그다음부터는 평소처럼 말하면 됩니다. "할 일 목록 만들어 줘" → AI가 작업 카드를 보여주고 확인을 받은 뒤 만들고,
확인 결과(✅·👀·❓)를 보여주고, 저장합니다. 망가지면 "아까로 되돌려 줘".

따라 하기 예시: [`examples/my-homepage/`](examples/my-homepage/WALKTHROUGH.md) -- 메모 → 할 일 → 가계부를 차례로 붙이며,
중간에 메모가 망가졌다가 되돌리는 과정까지.

## 주의
- 이 규칙은 AI가 **따르도록 안내**하는 것이지 강제하는 장치가 아닙니다. AI가 건너뛰면 "light-check 했어?"라고 물어 주세요.
- 화면이 보기 좋은지, 휴대폰에서 괜찮은지는 사람이 봐야 합니다. AI는 그런 항목을 "👀 직접 확인해 주세요"로 따로 부탁합니다.
- 비밀번호·API 키를 AI에게 코드로 넣게 하지 마세요. 규칙에도 들어 있습니다.

## 더 큰 프로젝트라면
팀 작업, 엄격한 검증 기록, 승인 절차, 공통 용어사전이 필요해지면 같은 생각을 무겁게 구현한
dev-process-framework(현재 비공개)로 옮겨 갈 수 있습니다. 개념은 그대로 이어집니다.

| light | framework |
|---|---|
| 작업 카드 (NOW.md) | task-new + 완료 기준(accept) |
| light-check | verify (실행 증거 기록) |
| light-save | finish (커밋·보고서·인수인계) |
| light-undo | 자기 변경 롤백 |
| 원인별 처리, 안 되면 되돌리기·빼기·나중에 | 원인 분류 · 재시도 · 대기 · Plan B · 종결(backlog) |
| NAMES.md | 공통 용어사전 |
| light-manual (`manual/`) | sk-dev-user-manual (`docs/manual/`, 필수 검사 user_manual) |
| 짝 스킬 data-light (`data/model.light.json`) | data-expert-framework 의 데이터 모델링 (`db/model.json`) -- `datalight.py upgrade` 로 옮김 |
| `NOW.md` 의 다섯 줄 (누가 쓰나·로그인·올리는 곳·개인정보) | 질문 대장 (`common.users`·`common.hosting`·`common.personal` …) |
| 작업 카드 `데이터: 새 표`, `데이터:` 저장 | `task-new --work-type data_model` (코드보다 정본 먼저) |
